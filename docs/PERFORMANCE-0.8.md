# Оптимизация 0.8 — замеры и план

Рабочий журнал оптимизации поверх завершённого функционала 0.8. Каждое изменение
принимается только с замером «до/после» и без изменения поведения (unit/e2e зелёные).
Замеры: production build, Linux-песочница, gzip -c для размеров.

## Намеченные шаги

1. **Горячий путь градиентов**: кеш скомпилированных точек прозрачности, убрать
   аллокации массивов на каждый семпл шума/градиента и лишнюю копию канваса
   у внешних обводок в `renderStyled`. Поведение и пиксели не меняются.
2. **Code-splitting диалогов**: тяжёлые модальные окна (стили, градиенты, пакет,
   шрифты, фильтры и т.д.) вынести из первичного чанка в lazy-чанки. Редактор,
   панели и холст остаются синхронными.
3. **Мемоизация предпросмотра градиента** в опциях инструмента и редакторе,
   чтобы перерисовки App не пересчитывали семплы без изменения данных.
4. Повторный замер, полная регрессия локально + Windows CI.

## Результаты

### Шаг 1 — горячий путь градиентов (коммит 2480457)

Парный микробенчмарк в одном процессе Node (старая версия из HEAD vs новая,
по два прогона, контрольные суммы результатов совпали до 3-го знака — выходные
пиксели не изменились):

| Семплирование | До | После |
| --- | ---: | ---: |
| `gradientColor`, 200 тыс. семплов | 25–38 мс | 12–20 мс (≈×2) |
| Шум Lab + прозрачность, 50 тыс. семплов | 91–102 мс | 63–94 мс (упирается в pow) |
| `gradientCss` ×48 семплов, 2 тыс. строк | 191–203 мс | 154–156 мс (−20%) |

`gradientColor` вызывается на каждый пиксель в коррекции «Карта градиента» и
заливке градиентом, поэтому ускорение ∝ площади изображения. Внешние обводки
больше не копируют полноразмерный канвас на каждый экземпляр обводки.

localhost-латентность, это честно фиксируем без прикрас.

### Отклонено по замерам (сознательно, с доказательствами)

1. **LUT для «Карты градиента»** по целочисленной яркости 30R+59G+11B
   (25 501 вход). Исчерпывающая проверка всех 16 777 216 цветов: float-разница
   ≤2,2e-16, но финальное округление точных «.5» меняет байт на ±1
   (например, чистый красный через чёрно-белый градиент: 76 → 77; всего
   150 727 канальных отличий при непрозрачности 100%). Это уже изменение
   пикселей, а не оптимизация — отклонено. Уровни/кривые/экспозиция при этом
   давно и точно работают через байтовые LUT, там вход канальный и таблицы
   по построению тождественны формуле.
2. **Прекомпилированный сэмплер градиента** (вынос WeakMap-lookup из
   попиксельного цикла коррекций). Побитово идентичен (0 байт-отличий на
   12 Мп во всех режимах), но медиана 5 прогонов показала ~4% *медленнее*
   (1427 vs 1371 мс): JIT хуже инлайнит замыкание. Откачено.
3. **Вынос рабочего пространства редактора за главный экран** (ленивая
   загрузка CanvasStage+панелей до открытия документа) — крупнейший
   потенциальный выигрыш стартового экрана, но требует разрезать монолитный
   App (≈3000 строк, общее состояние документа/истории/модалок). Накануне
   релиза риск регрессий несоразмерен; оставлено осознанным пунктом на 0.9.

## Третий круг (главный цикл коррекций)

### Принято (коммиты 368981b, 26e8219)

`applyCorrection` — самый горячий попиксельный цикл приложения: каждая
коррекция на каждый композит и экспорт. Два побитово идентичных изменения
(0 отличающихся байт на случайном 12-Мп буфере во всех режимах; теперь это ещё
и постоянный параметризованный unit-тест по всем типам коррекций):

1. **Специализированный быстрый цикл** для частого случая «нет маски +
   обычный режим наложения»: инвариантный `amount` и пустой вызов
   `blendCorrection('source-over')` вынесены из попиксельного пути при той же
   арифметике. Медианы 5 чередующихся прогонов на 12 Мп: инверсия −44%,
   уровни −8%, карта градиента −3%, ранний выход при opacity=0 −58%.
   Ветви с маской и остальными режимами наложения не изменены.
2. **In-place применение на пути рендера**: `renderCorrection` больше не платит
   две полнокадровые копии (копия внутри + `set()` обратно). Каждый выходной
   пиксель зависит только от того же входного, прочитанного до записи, поэтому
   результат побитово тот же; сверху ещё −2…16% и минус две аллокации по
   48 МБ на полнокадровое применение при 12 Мп.

Суммарно на типовых коррекциях 12-Мп кадра против начала круга: инверсия
431→207 мс, уровни 764→647 мс, карта градиента 1171→1052 мс (медианы этой
песочницы, методика та же).

### Аудит без изменений (измерено, трогать нечего или невыгодно)

- **Иконки lucide** — 11,2% главного чанка (~37,5 тыс. символов по sourcemap):
  честная цена используемого набора, tree-shaking работает; меньше можно
  только сменой набора иконок, это уже продуктовое изменение.
- **Диалоговый CSS** — 30,2% исходного CSS (~30 КБ исходника, ≈5 КБ gzip
  первичной загрузки) обслуживает только lazy-интерфейс. Вынос в lazy-CSS
  меняет порядок каскада против синхронных правил той же специфичности —
  риск тихих визуальных регрессий, не ловимых функциональными e2e, при
  выигрыше ~2,4% первичной загрузки. Отложено до визуальных снапшот-тестов.
- **История документа** — уже образцовый паттерн: неизменяемые команды делят
  строки пикселей по ссылке, бюджеты 128 МБ/вкладка и 256 МБ глобально с
  дедупликацией строк; `structuredClone` на каждое действие нет.
- **Морфология выделения** — уже O(n): точная евклидова дистанция
  (Felzenszwalb) + скользящий box blur в воркере.
- **Кисть** — переиспользуемые штампы вместо полнокадровых поверхностей;
  **гистограмма** — дебаунс 140 мс и предпросмотр ≤384 px. Менять нечего.
